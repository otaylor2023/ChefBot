ChefBot exploration contributions

A robot that cooks first has to know its kitchen: where every object is, and which of several like objects is which. We extended Olivia and Jack's agent harness so the robot builds that knowledge itself, from its own cameras, and we built the evals that check it did it right.

Status 28 October 2026. Code: branch explore-map (pushed up to the cabinet and door work; later commits are local on Simone's Mac) and branch explore-fixtures (worktree ChefBot-fixtures, local). Paths below are relative to the repo.

Concepts 1. Known kitchens 2. Full kitchens 3. Object memory Appendix

Concepts

The work follows three goals, each building on the one before:

Step 1Explore objects in a known kitchenThe robot knows the fixtures (counters, fridge, cabinets) and must find every loose object, with and without the ground truth detector. Step 2Explore a full kitchenThe robot knows nothing: it finds the fixtures too, and in the hardest version even builds its own floor map from depth. Step 3Remember objects across actionsOne record per object, so the robot can tell five forks apart, knows which one stirred the eggs, and can find or group them later.

Ideas shared by all three steps

  • Agent harness. Each turn the LLM sees a fixed system prompt, the tool list, the last 8 tool calls with their results, and a TASK STATE block rebuilt every turn from the robot's own records. It answers with exactly one tool call (go_to, detect, align, open, close, pick, place...), which runs on the robot. We reused the loop unchanged and added prompts, tools, a step checker and detectors.
  • Ground truth vs camera. The original detect read object names and positions from the simulator: perfect perception. We keep it only as a reference (the upper bound) and replace it with camera detectors that see only RGB and depth images.
  • No leaks. The robot starts from a map without objects. The true map is built from the simulator only after the run, read only by the scorer. A run guard makes any ground truth call raise. We never filter by the task's object list.
  • Free first. A scripted policy plays the LLM's role on a fixed route, so tools, detectors and scoring are tested at zero cost. Paid calls (Sonnet as a VLM) were capped and used sparingly.
  • Kitchens. RoboCasa layouts 1, 7, 25 and 39 (pictures in the appendix). Layout 1 has 6 objects; the others have 14: egg and milk in the fridge, a bowl in the microwave, nine things on counters, a plate in a cabinet and a fork in a drawer.
Step 1

Explore objects in a known kitchen

What
Starting from a map with the fixtures but no objects, find every loose object: its name, its position, and the fixture it is on or in, including inside the fridge, microwave, cabinets and drawers.
How
An exploration prompt and a coverage checker drive the robot to every fixture and behind every door; detect becomes open vocabulary and runs on camera images; each box becomes a 3D point from depth and is written into the robot's own map.
Code
chefbot/explore/ (prompt.md, coverage.py, vision.py, owl.py, siglip.py, sam3.py, look.py, score.py), entry point chefbot/scripts/explore.py, tool changes in chefbot/agent/tools/nav.py.

How the agent does it: prompt and tools

The exploration prompt is appended to Olivia's base prompt. It tells the agent to go_to each fixture, call detect() with no classes (which looks for all ~500 RoboCasa object names), open every door, look inside, close it, and cover both ends of long counters. complete lists what is left; the run ends with finish. Pick and place are not offered, so nothing is moved. Everything detect finds is written into the KITCHEN block of TASK STATE for the next turn.

The exploration prompt, verbatim 
EXPLORING THE KITCHEN (this run)
- This run comes before any cooking. The map you were given has the kitchen's fixtures
  (MAP PLACES) but none of its loose objects: food, cookware, utensils, dishes, bottles.
  Your job is to find all of them, so later tasks start from a complete map. Do not pick,
  place or move anything.
- Look at every fixture in MAP PLACES (burners are part of the stove: the stove covers
  them). For each one: go_to it, then detect() with no classes: with no classes it looks
  for every kind of thing it knows. Everything detect finds is written into KITCHEN for
  you; you do not record it yourself.
- Fixtures with a door (fridge, microwave, dishwasher, oven, cabinets, drawers) hide what
  is inside. For each: detect its handle (e.g. detect(["fridge handle"])), align to the
  handle, open it, detect() again to see inside, then close it before moving on. An open
  door often swings its handle out of view: then detect the fixture itself
  (detect(["fridge"])), align to it and close it by its own name (close("fridge")).
- A long counter may not be fully in view from one spot: complete names the part you
  have not seen; go_to an object you found near that part and detect() again from there.
- complete(step) tells you which fixtures you have not looked at or into yet, and which
  doors you left open. Keep going until it passes, then finish(summary) with a short list
  of what you found where.

Tools we added or changed for this: open vocabulary detect; go_to with part and along for long counters; closing a door by the fixture's name; doors that stop part way are "ajar" and stop blocking paths once closed; a re-seen object joins its map entry within 0.3 m; repeats get fresh names (fork_1, fork_2); and the map is saved as explored_map.yaml.

Models we implemented

All plug into the harness's Detector interface. A camera detector gives names and boxes; depth under the box gives the 3D point; edge, footprint and height filters drop junk; sightings are tracked across views and names voted per spot.

What worked

  • The route and tools reach almost everything: with ground truth perception the robot finds 13/14 on layout 7. Only one drawer fork and one stuck cabinet are out of reach.
  • With a camera, what is found is placed well: 2 to 4 cm median, almost always within 15 cm, heights within about 1 cm.
  • The VLM is the best namer: 91 to 100% right on objects over 1,000 px. Layout 1 is 6/6 for about $0.05.
  • The name vote was the cheapest big win: OWLv2 false finds 22 to 9 on layout 7, for free.
  • Close looks with the wrist camera added the spoon on layout 7 and cut the median error to 2.0 cm.

What did not

  • Small objects: under about 300 px (an egg or spoon at 1.4 m) they are rarely kept. Example: egg behind the arm.
  • Near synonyms: milk called "bottled water" by every model, even up close. Example.
  • OWLv2's naming: egg as "bar soap", lemon as "pear", many false finds on fixture parts. Example.
  • Going closer or zooming did not help OWLv2: with it the limit is the model, not the view.
  • SAM 3 names best (5% wrong) but is 23 times slower and swapped one gain for one loss (spoon found, apple called "cherry"). Example.
  • The pan is always 10 to 14 cm off, even for the exact detector: the true map stores its body origin, near the handle.

Step 2

Explore a full kitchen

What
Start with no fixtures on the map, find and name the sink, stove, fridge, counters and appliances (location, facing, footprint, burners), then find the objects on that self-made map.
How
Stage 1 keeps the floor grid and visits viewpoints along every obstacle; Stage 2 starts from nothing and builds the grid from depth with frontier exploration. Fixtures come from OWLv2 boxes plus one Sonnet label check each.
Code
Branch explore-fixtures: chefbot/explore/fixture_explorer.py, fixture_geometry.py, grid_builder.py (DepthGrid, ExplorePlanner, FrontierExplorer), fixture_score.py, leak_guard.py; entry point discover_fixtures.py (--build-grid for Stage 2).

Models we implemented

  • Fixture detector: OWLv2 with fixture words on three cameras per stop; depth points inside each box are snapped to the grid to give a footprint; views of the same fixture are fused; facing from the face normal seen in depth. One Sonnet check per fused fixture, on a crop with the box drawn in red (7 to 11 calls, under $0.01 per kitchen).
  • Burners: OWLv2 "stove burner" boxes on the cooktop from three stand points.
  • Grid from depth (Stage 2): every depth image becomes occupied or free evidence; A* plans through unknown cells at 3 times the cost; the robot drives to the cheapest frontier and looks around until none is left.
  • Objects: the VLM detector from step 1, with fixtures taken from the robot's own discovered map.

Evals we built

  • Fixture score: discovered fixtures matched to true ones by type and distance (Hungarian), then label, location error, facing error and footprint IoU. Pass bar: every fixture found and labeled, within 0.15 m, facing exact.
  • Grid score: IoU of the built grid against the true grid, free and occupied.
  • Usefulness: go_to every discovered fixture and check the robot ends within reach of the true one; then rerun object search on the discovered map and compare with the true map.
  • Leak guard: calling the ground truth detector, the map builders, or opening a semantic map file raises. 0 trips in every run.

What worked

  • Layouts 1 and 39 pass in both stages: every fixture found, labeled, within 0.15 m, facing exact.
  • All burners found in all 8 runs, within 3 cm.
  • The discovered map is as useful as the true one for finding objects (6 vs 5, 11 vs 11, 7 vs 7, 8 vs 9).
  • Stage 2 leaves no true free floor unknown; go_to reaches the true fixture almost every time.

What did not

  • Corner counter pieces (4 on layout 7, 2 on 25) and one seamless slab cannot be told apart in the images.
  • Fridge depth is the weakest number: 0.17 m off on layout 7 (OWLv2 boxes only its handles), 0.26 m on layout 25 in Stage 2.
  • Layout 7 Stage 2: Sonnet once calls the toaster oven a microwave; the toaster's facing is 90 degrees off.
  • Stage 2 is slow: 8 to 13 minutes per kitchen, against 2 to 7 for Stage 1.

Step 3

Remember objects across actions

What
Keep a record per object so the robot can tell like objects apart (five forks), remember what each was used for and its state (dirty, full, used up), and find or group them by category, use or plan.
How
A dict per instance next to the semantic map, filled only from the robot's own tool calls and detections; the tools log every use automatically; three new agent tools query it; it is saved per run and can be loaded into the next.
Code
chefbot/agent/world/objects.py (ObjectMemory), categories.yaml, hooks in agent/tools/nav.py and manip.py, tools in agent/tools/registry.py; tests chefbot/tests/agent/test_objects.py and test_object_confusion.py.

How it was built

  • Identity. Each instance keeps its map name (fork_1 to fork_5) through picks and places. A new sighting goes to the instance with the lowest cost: distance in metres plus 0.3 m times how unlike it looks. The look is a SigLIP 2 image embedding averaged over sightings, plus attributes such as colour when the detector gives them.
  • Uses. Every pick, place, lower_into, stir, squeeze and pour is logged on both objects (stirred on the fork, stirred_in on the bowl), with time, plan step and dish.
  • States. From each object's category: clean or dirty, empty to full, raw to used up. Some update on their own: a fork that stirs becomes dirty; pouring empties one container and fills the other; a cracked egg is used up and joins the bowl's contents.
  • Plans. An object can be set aside for a later step and ingredient, and released when done.
One record, as saved 
fork_1:
  label: fork
  category: cutlery
  attributes: {color: red}       # what tells it from the other forks
  signature: [...]               # SigLIP 2 look, mean of its sightings
  last_xy: [2.9, 0.3]
  last_where: counter_1          # or "gripper", or e.g. bowl
  states:
    clean: {value: dirty, source: you, t: 60}
  uses:
  - {t: 42, action: picked,       other: counter_1, step: s2, recipe: Scrambled eggs}
  - {t: 55, action: lowered_into, other: bowl,      step: s2, recipe: Scrambled eggs}
  - {t: 60, action: stirred,      other: bowl,      step: s2, recipe: Scrambled eggs}
  plans: []                      # e.g. {step: s5, ingredient: eggs} when set aside

How it is used

  • In the prompt: the KITCHEN block shows a short tag after an object once something is known, for example fork_1 [dirty; for s5 (eggs)]. Defaults are hidden so the prompt does not grow.
  • Agent tools: find_objects (by category, name, state, use, dish, step, or "not set aside"), object_info (full history of one object), note_object (set a state, set aside for a step, add a note).
  • Across runs: saved as runs/<run>/object_memory.yaml, loaded with --objects.

How effective it is: the confusion tests

Five forks, each with a hidden true identity; moves meant to mix them up; then one fork asked for by name or by use. The test checks which fork the robot ends up holding. Each case runs with identical forks and with forks that look different. Free, no LLM or VLM.

What worked

  • Right fork in 6 of 6 cases with different looks, 5 of 6 with identical forks.
  • The tests found and fixed three bugs: a new detection id could collide with a map name and hide an object; two things placed on one counter were both mapped at its middle (place now reports where the gripper let go); appearance weighed too little to re-find a fork moved far.

What did not, or is not done

  • Identical forks swapped out of view cannot be told apart by any camera; the memory then follows position and logs seen_moved.
  • Not yet run in the simulator; appearance thresholds still need tuning on real SigLIP 2 crops. The bug fix patch is not yet on the Mac.

C. Using the explored map: rearranging objects (layout 7)

These runs use the explored map for a first real job: pick objects up, put them on another counter, look again, and check the map is still right. They were recorded on 25 and 26 October, before the pick and place fixes of 27 October (which took the exact map run from 3 of 6 to 5 of 8 moves).
